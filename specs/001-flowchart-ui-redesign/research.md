# Research: Flowchart UI Redesign

## Decision 1: 리디자인 적용 범위는 편집 모드로 제한
- Decision: 편집 모드 UI만 리디자인하고 프레젠테이션 모드 시각 레이아웃은 유지한다.
- Rationale: 스펙 클라리피케이션에서 범위가 확정되었고, 기능 영향 없는 변경이라는 목표를 가장 안전하게 달성할 수 있다.
- Alternatives considered:
  - 편집+프레젠테이션 동시 리디자인: 범위 확대에 따른 회귀 위험 증가로 제외.
  - 프레젠테이션 우선 리디자인: 사용자 우선순위(P1 편집 경험)와 불일치로 제외.

## Decision 2: 시안 일치 기준은 구조/위계/간격 중심
- Decision: 픽셀 단위 복제를 강제하지 않고, 핵심 구조/정보 위계/간격 규칙 일치로 검수한다.
- Rationale: 다양한 화면 환경에서 안정적인 UI 품질을 유지하면서 과도한 미세 조정 비용을 줄일 수 있다.
- Alternatives considered:
  - 픽셀 완전 일치: 유지보수 비용이 높고 의미 없는 재작업 유발 가능성으로 제외.
  - 대략적 유사성만 허용: 품질 기준이 약해져 검수 일관성이 떨어져 제외.

## Decision 3: 성능 검증은 기준 빌드 대비 상대 비교
- Decision: 편집 화면 렌더/상호작용 성능은 기준 빌드 대비 악화 없음으로 관리한다.
- Rationale: 기존 성능 예산을 유지하면서 리디자인 영향 여부를 명확히 판단할 수 있다.
- Alternatives considered:
  - 절대 수치 고정: 환경 편차로 인한 오탐 가능성이 커 제외.
  - 성능 검증 생략: 헌장 성능 예산 원칙 위반으로 제외.

## Decision 4: 기능 동등성은 수동 체크리스트를 기본으로 검증
- Decision: 기능 동등성 판정은 수동 회귀 체크리스트를 기준으로 수행한다.
- Rationale: 스펙에서 검증 방식이 명시되어 있으며, UI 리디자인의 체감 품질 검증에 적합하다.
- Alternatives considered:
  - 자동 테스트만으로 판정: 시각/상호작용 검수 포인트가 누락될 수 있어 제외.
  - 수동+자동 동시 강제: 구현 단계에서 보완 가능하나 본 기능 수용 기준은 수동 판정으로 유지.

## Decision 5: 기술 선택 및 구현 경계
- Decision: 기존 React + Zustand + Vite 구조를 유지하고 `src/features/flowchart/components` 중심으로 변경한다.
- Rationale: 기능 회귀 위험 최소화와 변경 영향 추적에 유리하다.
- Alternatives considered:
  - 상태 구조 재설계 포함 대규모 리팩터링: 기능 영향 가능성이 높아 제외.
  - 별도 UI 프레임워크 도입: 요구사항(기능 영향 없음, 빠른 리디자인)과 불일치로 제외.
