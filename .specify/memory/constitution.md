# flowchart-app Constitution

## Core Principles

### I. 코드 품질 우선
모든 병합 가능 코드는 린트, 정적 분석, 타입 검사(적용 언어 한정)를 통과해야 한다.
중복 로직은 공통화하고, 함수/모듈은 단일 책임을 유지해야 하며, 순환 의존을 금지한다.
리뷰에서 품질 기준 미달이 확인되면 기능 완성 여부와 무관하게 반려한다.
이 원칙은 유지보수 비용과 결함 유입률을 동시에 낮추기 위한 비가역 기준이다.

### II. 테스트 표준 필수
모든 기능 변경은 최소 단위 테스트를 포함해야 하며, 사용자 흐름 변경은 통합 또는 E2E
테스트를 반드시 포함해야 한다. 버그 수정은 재발 방지 테스트를 먼저 추가하고 수정한다.
테스트가 없는 기능 PR은 예외 승인 없이 병합할 수 없다.
이 원칙은 회귀를 정량적으로 통제하고 배포 신뢰도를 유지하기 위한 필수 조건이다.

### III. 사용자 경험 일관성 보장
동일한 목적의 UI 요소는 화면 간 동일한 용어, 상호작용 패턴, 상태 피드백을 제공해야 한다.
오류 메시지, 버튼 문구, 폼 검증 피드백은 공통 규칙을 사용하고 임의 표현을 금지한다.
새 기능은 기존 UX 규칙과 충돌 시 신규 패턴을 도입하지 않고 기존 패턴에 맞춰 구현한다.
이 원칙은 학습 비용과 사용자 오류를 줄여 제품 신뢰도를 높인다.

### IV. 성능 예산 준수
기능 단위로 성능 목표를 사전에 정의해야 하며, 기본 응답/렌더링 경로는 p95 300ms 이하를
목표로 한다. 번들 크기, 메모리, 네트워크 호출 수는 변경 전후를 비교해 악화 시 원인과
완화 계획을 PR에 기록해야 한다. 성능 예산을 초과하는 변경은 승인 없이 병합할 수 없다.
이 원칙은 기능 추가 과정에서 성능 저하가 누적되는 구조적 위험을 방지한다.

### V. 한글 주석, 네이밍, 단순 구조
주석은 한국어로 작성하며, "무엇"이 아닌 "왜"를 설명해야 한다. 식별자 네이밍은
`PascalCase`(타입/컴포넌트), `camelCase`(변수/함수), `UPPER_SNAKE_CASE`(상수),
`kebab-case`(파일/폴더)를 기본으로 한다. 폴더 구조는 기능 중심 2단계 깊이를 기본으로 하고
불필요한 계층 분할을 금지한다.
이 원칙은 협업 가독성, 온보딩 속도, 변경 영향 추적성을 높이기 위한 표준이다.

## 기술 및 품질 표준

- 모든 PR은 체크리스트로 다음 항목을 검증해야 한다: 코드 품질, 테스트 증거, UX 일관성,
  성능 영향, 네이밍/구조 준수.
- 리뷰어는 최소 1명 이상이어야 하며, 아키텍처 또는 UX 규칙 변경은 2명 이상 승인을 요구한다.
- UI 변경 PR은 변경 전/후 스크린샷 또는 동등한 검증 자료를 포함해야 한다.
- 성능 검증은 로컬 또는 CI 측정치 중 재현 가능한 방식으로 기록해야 한다.

## 개발 워크플로 및 품질 게이트

1. `spec` 단계에서 사용자 시나리오, UX 일관성 기준, 성능 목표를 명시한다.
2. `plan` 단계에서 테스트 전략(단위/통합/E2E)과 성능 측정 방법을 확정한다.
3. `tasks` 단계에서 테스트 작업을 구현 작업과 동일한 우선순위로 배치한다.
4. 구현 단계에서 코드/테스트/문서를 함께 갱신하고, 한글 주석 및 네이밍 규칙을 점검한다.
5. 병합 전 품질 게이트(테스트 통과, 리뷰 승인, 성능/UX 검증)를 모두 만족해야 한다.

## Governance
이 헌장은 본 저장소의 개발 규칙에서 최상위 기준이며, 하위 문서는 본 헌장과 충돌할 수 없다.
개정은 변경 제안서, 영향 분석, 템플릿 동기화 결과를 포함한 PR로 수행한다.

버전 정책은 시맨틱 버저닝을 따른다.
- MAJOR: 원칙 삭제, 강제 규칙의 역호환 불가 변경
- MINOR: 원칙/섹션 추가 또는 강제 기준의 실질적 확장
- PATCH: 의미 변경 없는 문구 명확화, 오탈자, 비기능 편집

컴플라이언스 점검은 모든 PR에서 수행하며, 리뷰어는 헌장 체크 위반 시 승인할 수 없다.
반기 1회 이상 헌장-템플릿 정합성 감사를 수행하고 결과를 문서화한다.
